## 4. Findings

### 4.1 Bugs

#### BUG-1 — The clean-up also drops grammatical repeats (by design)

- **Decision (the maintainer, 2026-11-19):** this is a design choice, not a bug. The clean-up drops repetition,
  grammatical repeats included, and stays as it is. Recorded in DECISIONS.md, D53. The rest of this entry is kept as
  a record of the trade-off.

- **Where:**
  - [src/providers/transcription/local/mapper.ts:32](../src/providers/transcription/local/mapper.ts#L32) has
    `LEGITIMATE_DOUBLES = ['that', 'had']`;
  - the merge is at [:171–184](../src/providers/transcription/local/mapper.ts#L171);
  - the pref is [src/stores/settings.ts:69](../src/stores/settings.ts#L69): `localTextCleanUp`, `true`, with no UI.
- **What:** the clean-up keeps one copy of any word that one speaker says twice in a row, unless it's one of two
  English exceptions. The comparison ignores punctuation, so a comma between the copies doesn't stop it.
- **Probed** with the real mapper (one speaker, `cleanUp: true`):

  | Said | Becomes |
  |---|---|
  | Nous nous sommes rencontrés à Paris. | Nous sommes rencontrés à Paris. |
  | Vous vous souvenez de lui? | Vous souvenez de lui? |
  | Die, die ich kenne, sind hier. | Die ich kenne, sind hier. |
  | Ich weiß, dass das das Beste ist. | Ich weiß, dass das Beste ist. |
  | What it is is a problem. | What it is a problem. |
  | I had had enough. | I had had enough. ✓ |

- **Impact:**
  - French reflexives (*nous nous*, *vous vous*) are among the most common constructions in the language. German
    relative pronouns (*die die*, *das das*, *der der*) are frequent too. German and French are the first
    languages after English (Phase 36, L4).
  - The words are deleted silently, from the original transcript. Translation and summaries then work from the
    changed text.
  - The user can't turn the clean-up off, and the doc doesn't record that it ran (Phase 34's open note).
- **Suggestion:**
  - Since D56, a local run always knows its language, so pass the language in `MapOptions`.
  - Collapse repeats only where a language's list allows it, or only in English to start with. Never collapse
    across a comma.
  - Add `mapper.spec.ts` cases for the rows above.
  - Consider recording `cleanUp` in the request info, so a transcript says what was done to it.

#### BUG-2 — Choose file can wait for ever when the handover fails (Low)

- **Verified (2026-11-19)** before fixing:
  - Tauri 2.12.3's `with_webview` takes a closure that returns nothing. Its `Result` says only whether the closure
    was sent. The command, which runs off the main thread, queues it; the drop handler, on the main thread, runs it
    at once. Either way the error never got back.
  - The real `chooseRecording`, with Rust faked, never settled in three cases: nothing posted, no file handle, and
    `getFile()` rejecting.
  - In a release build `windows_subsystem = "windows"` means no console, so the `eprintln!` left no trace.
- **Fixed:**
  - Rust: `post_file` returns a receiver that the closure answers. If the closure never runs, it disconnects.
  - `stt_choose_recording` waits for that answer and fails with `recording`.
  - A drop is waited for on a blocking thread, then reported with a `describe.drop-failed` message. That's a plain
    `PostWebMessageAsJson`, which needs none of the newer interfaces.
  - The page: `chooseRecording` rejects with a `RecordingError` when the command fails, the handle is missing,
    `getFile()` rejects, or nothing arrives within 10 seconds. A drop's listener hears the same.
  - `FileDrop` shows "DeScribe couldn't open this file. Try again, or restart DeScribe if it keeps happening." with
    Technical details. It shows it in the compact picker too, and clears it on the next choice or drop.
  - Restarting helps when a WebView2 update is waiting: the app picks it up the next time it starts.
  - Tests: `recordings.spec.ts` and `desktopRecording.spec.ts` (new), and `FileDrop.spec.ts`'s desktop cases. In
    Rust: `choosing_waits_for_webview2_to_take_the_file`.
  - `npm run test:e2e`: 157 of 158 pass, as at `7466a65`. The one failure is TESTING.md's known intermittent one.
  - Not checked in the real app, and not on an old WebView2 runtime.
- **Where:**
  - Rust: [src-tauri/src/stt/recording.rs:188–190](../src-tauri/src/stt/recording.rs#L188) and
    [src-tauri/src/stt/commands.rs:156–158](../src-tauri/src/stt/commands.rs#L156);
  - the page: [src/desktop/recordings.ts:63–64](../src/desktop/recordings.ts#L63),
    [:85](../src/desktop/recordings.ts#L85) and [:102](../src/desktop/recordings.ts#L102).
- **What, on Rust's side:**
  - `post_file` runs inside `with_webview`, which only queues the closure. A failure inside it (a WebView2 runtime
    without `ICoreWebView2_23` or `ICoreWebView2Environment14`, or `CreateWebFileSystemFileHandle` refusing the
    file) is only `eprintln!`ed.
  - `stt_choose_recording` has already returned the token as a success.
- **What, on the page's side:**
  - `chooseRecording` waits on `waiting.set(token, resolve)` with no timeout.
  - `receive` returns quietly when the message has no file handle. A `getFile()` that rejects is only logged. In
    both cases the waiter is never resolved.
- **Impact:**
  - The Open dialog closes, and nothing happens: no file, no message.
  - `desktopRecording.choose()` catches only rejections ([src/stores/desktopRecording.ts:27–36](../src/stores/desktopRecording.ts#L27)).
  - A drop fails the same way, silently. A managed laptop can hold WebView2 at an older version, and that's when
    this would show.
- **Suggestion:**
  - Send the closure's result back on a one-shot channel and await it in the async command, so the command fails
    with a `recording` error.
  - On the page, reject the waiter on a timeout, or when `receive` fails for its token.

#### BUG-3 — A Cancel that reaches Rust early is lost (Low)

- **Verified (2026-11-19)** before fixing. There are two parts, and they differ in how often they happen:
  - **The early cancel:** confirmed in the code. `stt_cancel` runs on the main thread. `start()` takes the run's place
    on a blocking thread. Nothing orders the two, and a cancel to an empty place did nothing. But the gap is
    microseconds, a click can't land in it, and nothing in `src/` aborts a run by itself. So it was a latent race.
  - **The place held after a Cancel:** this one can happen. JobStatus puts **Start again** where **Cancel** was, so a
    double-click on Cancel sends `stt_start` while the worker is still being ended. That got `busy`.
  - Downloads don't have the second part: **Download** stays disabled until `stt_download` has returned.
- **Fixed:**
  - The page names each run and download with a `crypto.randomUUID()`. `stt_start`, `stt_cancel`, `stt_download` and
    `stt_download_cancel` take it.
  - Rust keeps a cancel that comes before its run or download, for that id only, and the last 8 at most. The run then
    fails with `cancelled` as it begins. A cancel that comes after its run has ended can't stop the next one.
  - A new run, download or removal waits up to 3 s for a cancelled run to leave its place. A run that wasn't
    cancelled is still refused with `busy` at once.
  - The run's and the download's places are freed by a guard's `Drop`, which also fixes DES-2. `is_running` recovers
    a poisoned lock, which fixes CQ-3.
  - The reload handler cancels whatever is running, with no id.
  - Tests:
    - Rust, seven new `exclusion_tests`: the early cancel, the run it names, the cap, the id check, the wait for a
      run, and the download's early cancel and wait.
    - `bridge.spec.ts`: each cancel names its run or download, and each run gets its own id.
  - Not checked in the real app.
- **Where:**
  - Rust: [src-tauri/src/stt/mod.rs:47–51](../src-tauri/src/stt/mod.rs#L47) and
    [:61–65](../src-tauri/src/stt/mod.rs#L61), and `start()` at
    [commands.rs:258–273](../src-tauri/src/stt/commands.rs#L258);
  - the page: [src/providers/transcription/local/bridge.ts:202–205](../src/providers/transcription/local/bridge.ts#L202)
    and [:226–229](../src/providers/transcription/local/bridge.ts#L226), and the job store at
    [src/stores/job.ts:231–236](../src/stores/job.ts#L231).
- **What:**
  - `stt_cancel` and `stt_download_cancel` act on whatever is registered at that moment.
  - The page sends them on abort, but `stt_start` and `stt_download` register only after `spawn_blocking` has
    started. `stt_cancel` is a sync command, so it runs on the main thread, and nothing orders the two.
  - Output shows **Preparing…** with Cancel at once, so a Cancel can arrive before `start()` takes the slot.
- **Impact, for a run:**
  - The job store shows *cancelled* at once, but the engine runs on to the end, unseen: minutes of CPU and a held
    power request.
  - Closing the window asks, because Rust is busy.
  - **Start again** fails with "Another transcription is already running on this computer."
- **Impact, for a download:** the band keeps its progress bar until Cancel is pressed again.
- **Also:**
  - The slot is cleared only after the worker has exited and its stderr thread has joined
    ([worker.rs:109–119](../src-tauri/src/stt/worker.rs#L109)).
  - So a **Start again** within that moment of a Cancel gets the same *busy* error.
  - The window is short in both cases. The consequence is the problem.
- **Suggestion:**
  - Give each run and download an id that the page passes to cancel. Or have Rust remember a cancel that came with
    nothing running, and have the next `start()` honour it once.
  - Have `start()` wait briefly for a slot that is being cleared, rather than refusing.

#### BUG-4 — Every write failure says "Not enough disk space" (Low)

- **Fixed:**
  - A new kind, `write`: "DeScribe couldn't save the speech models. Close other apps that might use them, and try
    again."
  - `download::io_error` reports `disk` only for 112, 39, `StorageFull` and `QuotaExceeded`. The free-space check
    is still `disk`. Every other file failure is `write`: in the download, a missing app folder, and **Remove**.
  - Tests:
    - Rust: `a_file_that_cannot_be_written_is_not_a_full_disk` (a folder where the `.part` goes), and
      `only_a_full_disk_is_disk` (112, 39, 5 and 32).
    - `downloadErrors.spec.ts`, `SpeechPackSection.spec.ts`: the new message.
  - Not checked in the real app.
- **Where:**
  - [src-tauri/src/stt/download.rs:200–204](../src-tauri/src/stt/download.rs#L200) and the `disk(…)` calls in
    `download`, `fetch` and `receive`;
  - [src/providers/transcription/local/downloadErrors.ts:22](../src/providers/transcription/local/downloadErrors.ts#L22).
- **What:**
  - Rust reports `disk` for every one of these: the app has no folder; a damaged file or a `.part` can't be deleted;
    the `.part` can't be opened, written or flushed; the file can't be renamed; the download can't be read back for
    its hash.
  - The page always shows "Not enough disk space: the speech models need 0.8 GB."
  - `disk_error` recognises `ERROR_DISK_FULL` (112) only in the detail, not `ERROR_HANDLE_DISK_FULL` (39).
- **Impact:** an antivirus holding the `.part`, a folder without write access, or a rename refused while something
  has the file open, each tells the user to free space they already have.
- **Suggestion:**
  - Keep `disk` for the free-space check and for 112 and 39.
  - Report other I/O failures as their own kind, for example `write`, with a message such as "DeScribe couldn't
    save the speech models. Close other apps that might use them, and try again." (as `toRemoveProviderError`
    already says).

#### BUG-5 — Auto-detect isn't restored after a restart (Low)

- **Verified (2026-11-19)** before fixing:
  - `autoReplaced` was a plain `let`, `false` on every start, while the `'en'` that replaced Auto-detect was saved.
  - After a restart, `'en'` loads, the start-up watcher sees nothing to change on either engine, and choosing
    ElevenLabs keeps English. That holds whether the speech pack's status comes before the store or after it.
  - The spec for D56's rule passed only because it never made a new store.
- **Fixed:**
  - The flag is saved in prefs as `languageAutoReplaced` (optional, `false` by default, so D18 doesn't apply), by a
    watcher of its own, so prefs written by other changes keep their shape. **Clear saved data** resets it.
  - At start with This computer chosen, ElevenLabs was in use until Rust answered: it gave Auto-detect back, and This
    computer then replaced it with English and set the flag again. Since BUG-6's fix, This computer is trusted from
    the start, so the language doesn't move.
  - Tests: four new cases in `settings.spec.ts`: a restart with the status coming after the store, and before it; a
    language chosen on this computer kept across a restart; and a reset. The first three fail without the fix.
  - Not checked in the real app.

- **Where:** [src/stores/settings.ts:241–270](../src/stores/settings.ts#L241), and the prefs save at
  [:274](../src/stores/settings.ts#L274).
- **What:**
  - With This computer, Auto-detect becomes English, and `autoReplaced` remembers that so ElevenLabs can bring it
    back (D56).
  - The flag lives only in memory, while the replacement (`'en'`) is saved to prefs at once.
- **Scenario:** the user chooses This computer, and Auto-detect becomes English. They restart DeScribe and choose
  ElevenLabs. English stays, although they never chose it.
- **Suggestion:** persist the flag with the prefs (an optional field is no shape change, by D18). Or save the
  user's own choice apart from the engine-adjusted one.

#### BUG-6 — Setup shows the ElevenLabs layout until the first status reply (Medium, was Low)

- **Verified (2026-11-19)** before fixing:
  - The status was asked for only when Setup or Settings' section opened, and `localAvailable` was false until it
    came, so the engine was ElevenLabs. Every point below holds on the first Setup of a session.
  - **Worse than written: a language can be lost.** The pack offers Lithuanian, Maltese and Slovenian, which
    ElevenLabs' list doesn't. With one of them saved on This computer, the store starts on ElevenLabs and turns it
    into Auto-detect. Rust then answers `ready`, and This computer replaces Auto-detect with English and saves it.
    The next local transcript runs as English, with only the Options summary to show it. Hence Medium.
  - The specs missed it: the test pack and the BUG-5 tests use languages both engines offer.
- **Fixed:**
  - `main.ts` asks for the status at start in the desktop build, while Home is open. Setup still asks each time it
    opens, and the two requests share one answer.
  - The speech-pack store's new `checked` is true once Rust has answered or failed to (`unreadable`).
  - Until then, `localAvailable` trusts the choice saved at start, so This computer is the engine, with its layout,
    languages and limits. If the models turn out to be missing or unreadable, it falls back to ElevenLabs as before:
    a real change, so the key band may then animate in.
  - While This computer waits for the answer, the footer says "Wait while the speech models are checked." and Next
    stays disabled, so no run starts on models not yet confirmed.
  - Tests:
    - `speechPack.spec.ts`: `checked`, after an answer and after a failure;
    - `settings.spec.ts`: five cases while Rust checks. A saved This computer is trusted and Next waits;
      ElevenLabs saved needs no wait; Lithuanian is kept; missing models give Auto-detect back; an unreadable status
      falls back. Four of them fail without the fix;
    - `SetupView.spec.ts`: This computer's layout before and after the answer, and the key band when the models are
      gone;
    - `fakeLocalBridge` gains `hold()` and `release()` to keep `status()` waiting.
  - Not checked in the real app.

- **Where:**
  - [src/stores/speechPack.ts:24](../src/stores/speechPack.ts#L24): the status starts `null`;
  - [src/stores/settings.ts:113](../src/stores/settings.ts#L113): `localAvailable`;
  - [src/ui/views/SetupView.vue:24](../src/ui/views/SetupView.vue#L24): the status is asked for only when Setup
    mounts.
- **What:**
  - Until Rust answers, the engine in use is ElevenLabs, whatever the saved choice.
  - So on the first Setup of each session, with This computer chosen:
    - the Transcribe with band is missing;
    - without an ElevenLabs key, the API key band animates in and back out;
    - Number of speakers and Zero retention appear for a moment;
    - Language briefly lists Auto-detect;
    - and the footer briefly says to add a key.
  - When the status check has to hash 821 MB (the first start after an update, or after a receipt mismatch), this
    lasts about a second on the PC, and longer on the work laptop.
- **Suggestion:**
  - Ask for the status once at app start in the desktop build.
  - Until the first answer, treat the saved choice as provisional: render none of the engine-dependent bands.

#### BUG-7 — Cancel can't stop the worker if the job object failed (Low)

- **Fixed:** without a job object, `Running` holds a copy of the worker's process handle, and Cancel calls
  `TerminateProcess` on it. The worker also exits (code 3) when a write to its stdout fails, so it ends once the app
  has closed or crashed. Checked by `worker.rs`'s `stopping` tests and `run.rs`'s.
- **Also:** while it went on, the next run waited, then was refused as `Busy`. Closing the window, too, relied only
  on the job ([lib.rs:73–74](../src-tauri/src/lib.rs#L73)).

- **Where:** [src-tauri/src/stt/worker.rs:71–79](../src-tauri/src/stt/worker.rs#L71) and
  [:27–42](../src-tauri/src/stt/worker.rs#L27).
- **What:**
  - `JobObject::for_child` returns `None` on any failure, and the run carries on.
  - `running.job` then stays 0, so `cancel()` only sets the flag. The stdout loop blocks until the worker finishes
    on its own.
  - Without `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, the worker also survives the app being closed or crashing.
- **Impact:** a rare environment (a policy on job objects, or a resource limit) gives a Cancel that does nothing and
  an engine process left running.
- **Suggestion:** keep the child's process handle in `Running` as well, and call `TerminateProcess` when there's no
  job. Or refuse to start (`engine`) when the job object can't be made.

### 4.2 Design flaws and robustness

#### DES-1 — Non-ASCII user folders and the model paths (Medium, unverified)

- **Verified, not a bug** (2026-11-19):
  - Both models load through ggml's `ggml_fopen`, which converts UTF-8 to wide characters and calls `_wfopen`. The
    DLLs' imports agree. The engine's narrow opens are all in features DeScribe doesn't use.
  - The opt-in test `run::tests::model_paths_with_non_ascii_letters_load` loads both models and a recording from
    `describe-Søren-Müller-æøå-<pid>\` on a code page 1252 PC, and fails when the path is mangled.
  - The evidence is in [reference/local-stt.md](reference/local-stt.md#non-ascii-paths-audit-des-1). No manifest
    change.
- **Where:** [src-tauri/src/stt/nemo.rs:201–204](../src-tauri/src/stt/nemo.rs#L201) (`c_path`), used by
  `Words::load` and `Speakers::load`.
- **What:**
  - The model paths reach the C API as UTF-8 bytes (`to_string_lossy` → `CString`).
  - On Windows, a narrow path is read in the ANSI code page, unless the library converts it from UTF-8 itself, or
    the process's manifest sets `activeCodePage` to UTF-8. It doesn't (`src-tauri/` has no such manifest entry).
  - ggml's own `ggml_fopen` converts UTF-8 to wide characters. Whether everything NeMo-Speech.cpp opens goes through
    it isn't recorded anywhere.
  - The models live under the user's profile (`…\AppData\Local\Packages\…\LocalCache\speech-pack\`).
- **Not affected:** the recording, which Media Foundation opens by a wide string, and the DLLs, which are loaded
  with `LoadLibraryExW`.
- **Impact if it fails:** colleagues whose Windows user name has a letter such as ø, æ, å, ü or é would get
  "Transcribing on this computer stopped unexpectedly" on every run, and nothing they do would fix it. That's
  plausible in Norway, Germany and France.
- **Suggestion:**
  - Check it once: set `DESCRIBE_SPEECH_PACK_DIR` to a folder named, say, `C:\Test-Søren-Müller\` in a debug build,
    and run a recording.
  - If it fails, add `<activeCodePage>UTF-8</activeCodePage>` to the exe's manifest (Windows 10 1903 and later; the
    worker is the same exe), or pass the short 8.3 path.
  - Record the result in reference/local-stt.md.

#### DES-2 — No drop guard on the run and download slots (Low)

- **Fixed** with BUG-3: `begin_run` and `begin_download` return a guard (`RunHeld`, `DownloadHeld`) whose `Drop` frees
  the place. The `Drop` also tells a run that is waiting for the place.

- **Where:** [src-tauri/src/stt/commands.rs:207–210](../src-tauri/src/stt/commands.rs#L207),
  [:243–251](../src-tauri/src/stt/commands.rs#L243) and [:270–271](../src-tauri/src/stt/commands.rs#L270).
- **What:**
  - The slot is cleared by the line after the work. A panic in between becomes a `JoinError`, mapped to
    `engine`, `offline` or `disk`, and leaves the slot `Some`.
  - From then on, every run, download and removal is refused until restart, and the close dialog asks for nothing.
  - No panic path is known today, so this is defensive.
- **Suggestion:** a small guard whose `Drop` clears the slot, made when the slot is taken.

#### DES-3 — Receipt file names aren't checked before deleting (Low)

- **Fixed:** `empty_pack_dir` skips any name that isn't one plain file name (`is_plain_name`), so neither **Remove**
  nor the clean-up after every download (`remove_other_packs`) can delete outside a pack's folder. A debug build's
  test list with such an id or file name is refused. `cargo test` covers both, and checks the compiled list.

- **Where:** [src-tauri/src/stt/pack.rs:403–417](../src-tauri/src/stt/pack.rs#L403),
  [:420–427](../src-tauri/src/stt/pack.rs#L420) and [:431–443](../src-tauri/src/stt/pack.rs#L431).
- **What:**
  - `remove`, `remove_other_packs` and `empty_pack_dir` join each `files[].file` from a `receipt.json` onto the
    pack folder, and delete the result.
  - `Path::join` with an absolute path replaces the base, and `..` climbs out of it. A corrupted or hand-edited
    receipt could make **Remove** delete a file outside the speech pack.
- **Impact:** only the user, or something running as them, can write the receipt, so this isn't a privilege
  boundary. But the module's promise ("only ever touch files a receipt or the list names") depends on it.
- **Suggestion:** when reading a receipt, accept only names that are a single normal path component.

#### DES-4 — A worker failure waits for the other threads (Low)

- **Fixed:** the app ends the worker as soon as it reads `Failed` (`read_events` in `worker.rs`, through the same
  stopper as Cancel), rather than wait for the pipe to close. The worker doesn't exit by itself: `process::exit` with
  the engine's threads mid-call would run the DLLs' shutdown code against locks they may hold. The comment on
  `collect` now says so. `cargo test` covers a failure ending the worker, and progress leaving it running.

- **Where:** [src-tauri/src/stt/run.rs:107–121](../src-tauri/src/stt/run.rs#L107) and
  [:68–78](../src-tauri/src/stt/run.rs#L68).
- **What:**
  - The comment says `collect` "returns at the first failure: the process then exits, which stops the other
    threads".
  - But `collect` runs inside `std::thread::scope`, which joins every thread before it returns. The `Failed` event
    is written only after that.
  - For example, a decoding failure at minute 20, or one model failing to load, is reported only once the other
    model has worked through its queue and its `finish()`. For the diarizer, that's a flush of the whole stream.
- **Impact:** bounded, but the error arrives late, and the comment is wrong.
- **Suggestion:** emit the failure from `collect` and `std::process::exit(1)` at once. Or fix the comment.

#### DES-5 — `Running::cancel` races the handle being closed (Low)

- **Fixed** with BUG-7: `Running` keeps its stopper (the job object, or the process handle) in a
  `Mutex<Option<…>>`. Cancel uses it, and `run` drops it, only under the lock.

- **Where:** [src-tauri/src/stt/worker.rs:27–42](../src-tauri/src/stt/worker.rs#L27) and
  [:114–116](../src-tauri/src/stt/worker.rs#L114).
- **What:**
  - `cancel()` loads the job handle, then calls `TerminateJobObject`.
  - `run` sets the slot to 0, then closes the handle. Nothing stops the two interleaving.
  - So a cancel that arrives as the worker ends on its own can terminate a closed, or reused, handle value. The
    SAFETY comment ("set to 0 first") doesn't make the load and the call one step.
- **Impact:** the practical risk is tiny: the value would have to be reused by another job object in that moment.
  It is still unsound `unsafe`.
- **The download's request handle:** `Downloading::cancel` against `Response::read` (download.rs:109–115,
  589–610) follows WinHTTP's documented way to cancel a synchronous call (close the handle from another thread),
  and is fine.
- **Suggestion:** hold the `JobObject` in a `Mutex<Option<JobObject>>` inside `Running`. Terminate it and drop it
  under the lock.

### 4.3 Performance

#### PERF-1 — One long speaker segment slows the join about 7× (Low)

- **Where:** [src/providers/transcription/local/mapper.ts:102–104](../src/providers/transcription/local/mapper.ts#L102).
- **What:**
  - `place()` skips segments whose *end* is more than 30 s before the word, but the segments are sorted by
    *start*.
  - One long early segment stops `from` moving. Every later word then scans every segment from there to 30 s past
    itself.
- **Measured** with 75,000 words over 3 hours and 3,000 turns, on the maintainer's PC:
  - 68 ms with ordinary turns;
  - 508 ms with one extra segment over the whole recording.

  The join runs on the UI thread when a run ends, so the laptop would freeze for a second or more.
- **Suggestion:** keep a list of the segments that are open, ordered by end, and drop from it as words advance. Or
  sort a second index by end. Add the long-segment case to the 25k-word speed test.

## 5. Checked and found sound

These were looked at specifically and need no change:

- **Downloads:**
  - only `pack.json`'s URLs, each checked by `is_pinned` (HTTPS, `huggingface.co`, a 40-character commit, the
    listed file name) and tested;
  - redirects followed by hand, over HTTPS only, at most ten;
  - nothing in the request about the user;
  - the size checked before writing and as bytes arrive;
  - SHA-256 checked before the rename;
  - a wrong file deleted, never loaded;
  - a `.part` resumed with a `Content-Range` that must fit;
  - an HTML answer refused;
  - revocation deliberately off, as Phase 33 found it must be.
- **The command surface:**
  - eight commands;
  - `COMMANDS`, `build.rs`, `lib.rs` and the capability kept in step by a test;
  - none takes a path, URL or host;
  - recordings named by an unguessable token, kept 24 h and at most eight.
- **The web build:**
  - everything that reaches Tauri sits behind `__DESKTOP__`;
  - schemas are made at first use, not at import;
  - `verify:single-file` rejects Tauri's globals, the command names, a model's file name and the Settings band's
    text.
- **Validation:** every reply, progress message and error from Rust is parsed with zod (finite numbers,
  non-negative counts, known kinds). Anything unexpected becomes an `engine`, or `offline`, error with a shortened
  detail.
- **Mutual exclusion:**
  - a run, a download and a removal can't overlap;
  - the lock order is always `running`, then `download`;
  - F5 cancels both, since the page that owned them is gone;
  - the close guard asks during either.
- **Lifetimes:**
  - `KeepAwake` is released by `Drop` on every path;
  - the worker is in a kill-on-close job object, so it can't outlive the app. Without one, Cancel ends the process, and the
    worker ends itself once its pipe to the app is gone (BUG-7);
  - the worker's stderr is read on its own thread, so neither pipe can fill and block it.
- **Chunking:** the 30 s pieces with a 2 s overlap tile the recording with no gap and no double-kept word, and the
  tests prove it for several block sizes.
- **The pack folder:**
  - the receipt avoids hashing at every start;
  - a partly downloaded pack is *missing*, not *damaged*;
  - another version's folder is removed only after the new files check out;
  - stale `.part` files are cleaned at start;
  - **Remove** leaves files that nothing names.
- **FFI:** the structs' sizes are tested against MSVC x64, `gpu: -1` is set explicitly, and the options' size is
  checked against what the DLL returns.
- **Stale results:** the job store's `isCurrent()` drops progress and results from a cancelled or older run.
  **Try again** reuses the recording's token, which Rust keeps.
- **Both builds read a local transcript:** `provider` is any non-empty string (D52). The header and the export name
  the engine, and an unknown pack is shown by its id. Every pack language has a display name (checked: all 25).
