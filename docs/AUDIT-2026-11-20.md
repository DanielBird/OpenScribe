The phase is carefully built. The decisions that carry the risk are sound:

- **Two engines** keep the processor's build byte for byte and keep a missing `vulkan-1.dll` from taking the processor
  down with it. `build-stt-runtime.ps1` now proves the import chains with `dumpbin`, both ways.
- **The probe is a process** with a deadline, so a driver that crashes or hangs while listing can't take the app with
  it.
- **One engine per worker.** The worker never meets both sets of same-named DLLs.
- **Loads one at a time on a card.** The `Loading` lock in `run.rs` fixes the `ggml_vk_get_device` race that Task 3
  found, and only on a card.
- **Every reply from Rust is parsed with zod.** `stt_devices` takes nothing from the page, and the card's name is only
  compared, never used as a path.
- **Tests at every layer.** The tests cover each layer's new behaviour, including the fallback (`run_job`), the error
  mapping, two identical cards, an unreadable pref and an old `lastLocalRun` record.

## 4. Findings

### 4.1 Bugs

<a id="gpu-1"></a>
#### GPU-1 · Medium · A failure that isn't the card's is reported as the card's

`commands.rs` `on_a_card()` turns every `Engine` and `OutOfMemory` error in a run on a card into `gpu`. But `Engine` is
also what these failures give, none of them the card's:

- **Media Foundation failing to start:** `run.rs` `decode_failure()` gives `Engine` when `error.stage` starts with
  "starting Media Foundation".
- **Starting the worker:** `worker.rs` gives `Engine` for "finding the app: …" and "starting the engine: …".
- **A worker thread that ends without a result:** "a part of the engine stopped without a result" (`collect()`).
  *Correction, on fixing:* a decoder thread that panics doesn't reach this message. `std::thread::scope` panics again
  when the threads are joined, so the worker dies, and `crashed()`'s `Engine` became `gpu`. The effect is the same.
  The message itself is near unreachable, since every thread sends something on every path.

**What goes wrong:** the user reads "The graphics card (AMD Radeon 740M Graphics) stopped while transcribing.". The
User Guide tells them to update the card's driver or choose **Processor**. **Try on the processor** then fails the same
way, with "Transcribing on this computer stopped unexpectedly.". Settings still says the card, so they may give up on
it for nothing. D41's technical details say the truth, but behind a `<details>`.

**Fix:** classify where the origin is known. In `run.rs`, give the models' failures (`engine_failure()` from
`words_thread` and `speakers_thread`) the `gpu` kind when `gpu != PROCESSOR`, and leave the decoder's alone. Then
`on_a_card()` maps only what the worker can't say itself: `crashed()`'s `Engine` and `OutOfMemory`, a worker that died
mid-run. Add a test where a card run's Media Foundation failure stays `engine`.

**Resolved (2026-11-20):** as above. `run.rs` gives `gpu` for the models' failures and for the Vulkan engine not
loading on a card. `worker::run` turns only a crash on a card into `gpu` (`worker::on_a_card`), and `run_job` passes
errors through. A decoder panic on a card still reads as the card's (see the correction above), which is noted in the
phase's Handoff. Tests: `a_models_failure_is_the_cards_only_on_a_card`, `a_crash_on_a_card_is_the_cards`,
`a_failure_on_a_card_comes_back_as_the_worker_gave_it`.

<a id="gpu-5"></a>
#### GPU-5 · Low · One card with no description hides every card

`nemo.rs` `Registry::list()` turns a null description into `""`, and `gpus()` keeps it. The page's schema
(`bridge.ts`, `gpuDevice.name: z.string().min(1)`) rejects the whole array for that one entry. `settings.refreshDevices()`
then catches the error, warns, and lists nothing. A driver that leaves the description empty would therefore hide
every card on that computer, the good ones included, with no message. None of the PC's drivers does this; it's a
robustness gap, not an observed failure.

**Fix:** in Rust, name such a device rather than send an empty name. The `ggml_backend_dev_name` export would give, say,
"Vulkan1", or `gpus()` could drop it. Add an `only_graphics_cards_are_listed…` case with an empty description. The
saved choice and `gpu_index` both use the same name, so either fix stays consistent.

*Correction, on verifying:* dropping the device isn't consistent. `gpu_index` is a card's place in `gpus()`, the
engine's own count, so dropping an unnamed card would move every card after it to the one before, and a run would load
on the wrong card. A description of only spaces is empty too, since `list()` trims it.

**Resolved (2026-11-20):** `gpus()` names such a card by its place among the cards, "Graphics card 2", rather than use
ggml's "Vulkan1", which needs another export and reads poorly in **Run on**. The page is unchanged. Tests:
`a_card_with_no_description_is_named_by_its_place`, `a_card_with_no_description_keeps_the_cards_after_it_in_place`.

<a id="gpu-7"></a>
#### GPU-7 · Low · `-Only vulkan -From` can write a `built.json` that the pack refuses

`build-stt-runtime.ps1`: with `-From`, the Vulkan SDK's version is read from the `CMakeCache.txt` beside `bin\`. Either
of these writes `vulkanSdk: "unknown"`:

- no `CMakeCache.txt` beside it (only a warning);
- a cache whose Vulkan paths don't contain `VulkanSDK\<version>\` (a custom install folder).

`pack-desktop.mjs` then refuses with "built with Vulkan SDK unknown, but stt-runtime.json names 1.4.363.0". The copy
looks like it worked, and the failure comes later, in another script.

**Fix:** stop in `build-stt-runtime.ps1` when the SDK can't be determined for a Vulkan `-From`, with what to do (copy a
build that has its `CMakeCache.txt`, or build it here). Or take a `-VulkanSdk <version>` that the user vouches for.

### 4.2 Design flaws and robustness

<a id="gpu-2"></a>
#### GPU-2 · Low · A run on a card has no deadline while it finds the card

The probe got a process and a 15 s deadline because "a driver that crashes or hangs while listing" is the risk (decision
2). A run on a card does the same listing in the worker (`run.rs` `card_index()` → `Registry::load()` →
`ggml_backend_dev_count`, which starts the Vulkan instance), with no deadline. `worker::run` waits for events with no
timeout before `Started` or `DeviceMissing`.

**What goes wrong:** on the driver the probe guards against, the run sits at *Preparing* with no time left until the
user clicks Cancel. A crash is handled: it becomes `gpu`. Only a hang isn't.

Also, `job.ts` sends the saved card even when Settings' last probe didn't list it. A colleague whose laptop is undocked
therefore pays a Vulkan start (0.2–0.5 s here, more on a slow driver) before every run falls back. That much is decision
5's choice, and cheap.

**Fix (if wanted):** in `worker::run`, for a job with a device, end the worker if neither `Started` nor `DeviceMissing`
arrives within `DEVICES_TIMEOUT`, and treat that as `DeviceMissing`: the processor then runs it, as decision 5 says for
a missing card.

*Corrections, on verifying:*
- The Vulkan start is in `Registry::list()`, at its first `ggml_backend_dev_count`. `Registry::load()` only loads the
  DLLs.
- `Started` is the wrong end for the deadline. It waits for Media Foundation to open the recording, and a OneDrive file
  that's online-only downloads first, which could pass 15 s and silently move the run to the processor.
- Ending the worker isn't enough. A hang in the kernel driver might not let it end, and then `read_events` and
  `child.wait()` block anyway.
- On a hanging driver the cost of sending the saved card is 15 s on every run, not 0.2–0.5 s, since the probe lists
  nothing but the pref is still sent.

**Resolved (2026-11-20):** the worker sends a new event, `device-found`, as soon as it has found the job's card, and the
deadline (`worker::LISTING_TIMEOUT`, 15 s) runs until `device-found` or `device-missing`. Past it, `worker::run` ends
the worker without waiting for it (stdout is read on its own thread) and returns `Finished::ListingHung`, which
`run_job` runs on the processor. It also sets `Stt::listing_hung`: until the app restarts, runs skip the card and
`stt_devices` lists none without probing. A probe that times out sets it too. A hang after `device-found`, while a
model creates the card's device, is left to Cancel (the phase's Handoff).

<a id="gpu-3"></a>
#### GPU-3 · Low · The silent fallback leaves no trace of why

`DeviceMissing` covers two different things: the card isn't listed (expected: an undocked laptop), and the Vulkan
engine won't load at all (unexpected: a DLL missing after an update, a broken loader). Each cause gets only an
`eprintln!` in `run.rs` `cards()`, which goes nowhere:

- the probe's stderr is `Stdio::null()` (`worker::devices`);
- a run's stderr is kept only for a crash's detail, and `DeviceMissing` isn't a crash.

Settings then hides **Run on** (no cards listed), and runs quietly use the processor. The user sees only that the card
has disappeared from Settings. A maintainer helping them has nothing to read.

Decision 5 rules out a message to the user, and this keeps to it.

**Fix:** keep it silent for the user, but leave a trace for the maintainer:
- carry the reason in the `DeviceMissing` event (`{ reason }`);
- have `stt_devices` log the probe's last stderr lines with `console.warn` on the page when the Vulkan engine exists but
  lists nothing because it failed to load;
- optionally, record the fallback in the run's timings (say `requestedDevice`), so Timings could tell "ran on the
  processor" from "fell back to it".

*Correction, on verifying:* `console.warn` on the page wouldn't reach a maintainer. The release build has no DevTools
(`tauri` without the `devtools` feature), so the trace has to be in the app. Since GPU-2, a hang and a session that
skips the card after one fall back silently too, and so does a saved card with no Vulkan engine installed.

**Resolved (2026-11-20):** `device-missing` carries a `reason`. `run_job` and `job_for` give one for a hang, a skip after
a hang and a missing Vulkan engine. The run's timings gain `fellBack: { device, reason }`, and Settings' **Timings**
shows "Processor (8 threads), not <card>" with a **Why** row, still with no message. The probe's own reason is left out:
it would need new UI while **Run on** is hidden. See the phase's Handoff.

<a id="gpu-4"></a>
#### GPU-4 · Low · The saved card can't be cleared while it's gone

With the saved card missing from the list, `checkedDevice` checks **Processor** and keeps the saved card (decision 4).
The radios bind `:checked` and save on `@change`. A click on a radio that is already checked fires no `change` event,
so the user can't choose **Processor** for good while the card is away:

- A colleague undocks, opens Settings, sees **Processor** checked and clicks it to be sure. Nothing is saved.
- They dock again, and the next run is on the card, though Settings last showed **Processor**.
- If no card is listed at all, the group is hidden, so there's nothing to click anyway.

Decision 4 wants the card to come back with the card, and it does. The flaw is only that an explicit click on
**Processor** is lost.

**Fix:** save on `@click` as well as `@change` for the Processor radio, or always call `setLocalDevice` on `click`
(`setLocalDevice` is idempotent). Add a spec for "the saved card is gone, Processor clicked, the card returns: still the
processor".

**Resolved (2026-11-20):** every **Run on** radio saves on `click` as well as `change` (`change` kept for arrow keys),
and `setLocalDevice` does nothing for the choice already saved, so the second event writes nothing. With no card
listed the group is still hidden, as decision 4 wants. The User Guide says a choice of **Processor** keeps the card
from coming back. Tests: the spec above in `SpeechPackSection.spec.ts` (it fails without the fix), and one in
`settings.spec.ts` for the processor saved and the same choice not written again.

<a id="gpu-6"></a>
#### GPU-6 · Low · Two identical cards are told apart only in the radio group

`deviceOptionsFor()` labels a repeated name "NVIDIA RTX A2000 (2)". That label stays in Settings:

- the failure message uses `input.device.name` (`provider.ts`), without the number;
- **Ran on** uses `timings.device`, the name only (`SpeechPackSection.vue` `ranOn()`).

On a workstation with two identical cards, neither says which one failed or ran. This is rare, as the phase says, and
D13 argues against the number where it doesn't help. Still, the message is where it would help most.

**Fix:** carry `nth` with the name (`timings.device` as `{ name, nth }`, or the label made in one place and reused).
Otherwise, write the limitation down in the Handoff.

*Correction, on verifying:* there is a third place. Since GPU-3, a run that fell back says "Processor (8 threads), not
<card>" from `fellBack.device`, the name alone too (`commands.rs` `requested`).

**Resolved (2026-11-20):** both, as above. `cardLabel({ name, nth })` in `src/domain/gpuCard.ts` makes the label for
**Run on**, the failure message and **Ran on**. Rust sends `timings.device` and `fellBack.device` as `{ name, nth }`, and
the `lastLocalRun` record reads an older name-only card as `nth` 0. The message for a second identical card has nested
parentheses, "The graphics card (NVIDIA RTX A2000 (2)) stopped…", only on such a PC. Tests: `gpuCard.spec.ts`, and
second-card cases in the bridge, provider, job store, `SpeechPackSection` and Rust timings specs.

<a id="gpu-9"></a>
#### GPU-9 · Nit · Settings probes the cards on every visit

`SpeechPackSection` calls `refreshDevices()` whenever it mounts in *ready*. That's every visit to Settings, including
during a run on the card, so each visit starts a process that loads the Vulkan engine (227–440 ms here; up to the 15 s
deadline on a driver that hangs). `refreshDevices()` shares a request already in flight, but keeps no result between
visits. This is decision 2 as written, and the cost is small. The probe during a run on the same card is the only part
worth noting. Nothing went wrong in Task 5, but the maintainer's G2 and G4 in the app could include one visit to
Settings during a run.

**Fix (if wanted):** keep the list for the session, and refresh it when the models change or on a window focus after a
display change.

<a id="gpu-8"></a>
#### GPU-8 · Nit · The fake engine and the real probe disagree in a debug build

With `DESCRIBE_STT_FAKE` set and `DESCRIBE_STT_FAKE_DEVICES` unset, the two sides use different lists:

- `stt_devices` lists the **real** cards (`devices_now()` falls through to the probe);
- the fake worker's `fake_card_missing()` checks the job's card against `fake::devices().unwrap_or_default()`, an
  **empty** list.

Every run on a listed card then falls back to the processor silently. That reads like the G6 behaviour, but it is
wrong. It's debug only, and the phase's G rows always set both variables, so it hasn't misled anyone yet.

**Fix:** in the fake worker, treat an unset `DESCRIBE_STT_FAKE_DEVICES` as "any card is there". Or document in
desktop.md's debug switches that the two must be set together.

## 5. Checked and found sound

- **The fallback loop:** `run_job` falls back at most once (`processor: None` on the second call). A cancel between
  the two workers is honoured, since `worker::run` checks `is_cancelled()` before spawning. Progress, the keep-awake
  and the close guard cover both workers.
- **`DeviceMissing` ends the worker at once** (`read_events` calls `running.end()`), like `Failed`. A test covers it.
- **Old shapes still read:**
  - a job without `device` runs on the processor;
  - `Timings.threads` can be missing or null;
  - `lastLocalRun` from before Phase 37 reads as the processor (`device` with `.catch(null)`);
  - `localDevice` that won't parse reads as `'cpu'`.
- **The web build:** the button's label is a `__DESKTOP__ ? … : ''` constant, the bridge is desktop-only, and
  `verify:single-file` finds neither marker.
- **The device index:** `gpu_index` counts GPU and integrated-GPU devices in ggml's order, skipping the CPU, ACCEL and
  META types, as `backend.cpp` does. The tests cover two identical cards and a missing one. The worker lists the
  registry on the main thread before the model threads start, so the Vulkan instance is created once.
- **DLL loading:** `Registry::load` and `Api::load` load from the same folder by full path with
  `LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR | SYSTEM32`, so `nemo_speech_asr_c.dll`'s import of `ggml.dll` binds to the module
  already loaded. `extern "C"` and `extern "system"` are the same ABI on x64.
- **Packing and notices:** each engine is checked against its own `built.json` (version, backend, SDK, sizes, SHA-256)
  before anything is staged. `make-notices.mjs` stops on another Vulkan SDK. The new notice entries match what
  `ggml-vulkan.dll` compiles in.
- **The pref and the run:** `job.ts` sends the card only to the local provider, and copies it. `retryOnProcessor()`
  does nothing during a run or after an ElevenLabs run. **Try again** after it repeats the processor run, as the Handoff
  says.
- **Accessibility:** **Run on** is a `<fieldset>` with a visible `<legend>` and real radios sharing one `name`, and
  **Try on the processor** is a real button in the existing live region's action row.
