## 4. Findings

### 4.1 Bugs

#### BUG-1 — Two e2e specs fail on main (High)

- **Where:** [tests/e2e/project.e2e.ts:52](../tests/e2e/project.e2e.ts#L52),
  [tests/e2e/shell.e2e.ts:64](../tests/e2e/shell.e2e.ts#L64); the copy is in
  [src/ui/views/ProjectView.vue:168](../src/ui/views/ProjectView.vue#L168).
- **What:** both specs wait for "A project can be a local folder or a shared one, for example in OneDrive." The
  component says "A project can be a local or shared folder." Commit `f895a2c` set that copy but updated the unit
  spec and both e2e specs to the longer wording; `67d13a5` corrected the unit spec only.
- **Impact:** AGENTS.md's Definition of Done is broken on main. `npm run release` runs Playwright
  ([scripts/release.mjs:54](../scripts/release.mjs#L54)), so the next HTML release fails at the last step.
  `desktop:pack` doesn't run e2e, so the 1.1.0 MSIX in `release/` (built at 21:53, after this commit) was packed
  without this gate.
- **Suggestion:** update the two strings; consider running the e2e suite in `pack-desktop.mjs` too.
- **Status:** Fixed on 3 November 2026. Both e2e specs now expect the component's copy, "A project can be a local
  or shared folder.", and the chromium suite passes (134 passed). Running e2e in `pack-desktop.mjs` was not taken
  up: `desktop:pack` still doesn't run e2e.

#### BUG-2 — A summary can be stamped with a brief it wasn't made with (Medium)

- **Where:** [src/stores/pipeline.ts:372–391](../src/stores/pipeline.ts#L372).
- **What:** `summariseStep` captures `open = project.project` and sends `open.brief`, then, after the model replies
  (often a minute or more), writes `briefHash: project.briefHash` — the hash of whatever brief is current *then*.
- **Scenario:** during **Summarise all**, someone saves the Brief dialog, or a background rescan picks up a
  colleague's brief edit (`refresh()` → `setProject`). Every summary that was in flight is saved with the new
  brief's hash although it answered the old research questions. `groupSessions` marks it `ok`, so **Regenerate**
  is never offered for it. D21 depends on this hash to say when a summary is out of date.
- **Suggestion:** compute `briefHash(open.brief)` when `open` is captured, and write that.
- **Status:** Fixed on 3 November 2026. `summariseStep` computes `briefHash(open.brief)` from the brief it sends and
  writes that, so a summary in flight when the brief changes is saved as out of date and **Regenerate** is offered.
  The project store's `briefHash` export had no other reader and was removed. Covered by "stamps a summary with the
  brief it was made with, when the brief changes meanwhile" in `pipeline.spec.ts`.

#### BUG-3 — A pipeline translation can be attached to text it wasn't made from (Medium)

- **Where:** [src/stores/pipeline.ts:318](../src/stores/pipeline.ts#L318) and
  [:342–347](../src/stores/pipeline.ts#L342).
- **What:** for a session that isn't open on Output, `translateStep` reads the transcript, translates it (minutes
  for a long session), then reads the file *again* and saves `{ ...secondRead.doc, translations: { en } }` with the
  second read's stat as the expected stat.
- **Scenario:** a colleague edits turns or renames speakers while the translation runs, and OneDrive syncs it. The
  second read sees their version, the change check compares against that same version and passes, and the
  translation of the old text is saved onto the new text. The summary step that follows then quotes stale English
  (see DES-2), with nothing on screen to say so.
- **Suggestion:** keep the first read's stat and pass it as `expected` (a `changed` error then fails the step and
  Resume re-reads), or compare `transcriptHash` of the two reads before merging.
- **Status:** Fixed on 3 November 2026 with the second suggestion. Before writing the translation into the file,
  `translateStep` compares the `transcriptHash` of the file it reads then with that of the text it translated. This
  also covers a session replaced on Output meanwhile, which has no first-read stat. If they differ, the step fails
  with `changed` ("Someone else changed this file since DeScribe read it.") and keeps only the translations of turns
  whose text didn't change. **Resume** then re-translates only the batches with changed turns. Re-using the whole
  stored translation would have recreated the bug one click later. The second read's stat is still passed as
  `expected`, so a write after that read fails too. Covered by "doesn't attach a translation to text a colleague
  changed meanwhile; Resume translates what changed" in `pipeline.spec.ts`.

#### BUG-4 — A new transcription discards project edits that haven't been saved to the folder (Medium)

- **Where:** [src/ui/views/GlossaryView.vue:25–40](../src/ui/views/GlossaryView.vue#L25),
  [src/stores/transcript.ts:201–211](../src/stores/transcript.ts#L201) (`setDoc`).
- **What:** **Run** asks "Start a new transcription? This replaces your last transcript." It doesn't look at the
  folder state. `setDoc` cancels any pending save, drops the project link and overwrites the IndexedDB copy.
- **Scenario:** after a browser restart (access to the folder lapses on `file://`, T14) a researcher fixes names in
  a project transcript on Output without pressing **Reconnect**, then starts another recording. The edits were
  only in IndexedDB and are gone. Output does show the **Reconnect** notice meanwhile, but the Run confirmation, the
  point where the edits are about to be lost, doesn't mention it.
  [SessionSummary.vue:146–156](../src/ui/components/SessionSummary.vue#L146) handles this case for **Open
  transcript** with a red "Its latest changes aren't saved in its project" confirmation; **Run** and **Clear saved
  data** don't.
- **Suggestion:** give GlossaryView's confirmation and the Clear saved data confirmation the same warning. Open
  transcript's condition is `!transcript.projectLink || transcript.folderNotice`; for these two, the project-link
  half is what matters, and `transcript.projectLink && (transcript.folderNotice || transcript.folderUnsaved)` also
  covers a save still waiting for the project to load.
- **Status:** Fixed on 3 November 2026. The transcript store has a new computed, `unsavedInProject`, which is the
  condition above. When it is true, Run's confirmation adds Open transcript's sentence, "Its latest changes aren't
  saved in its project.", and turns red with focus on Cancel. Clear saved data's confirmation, which was already red,
  adds "Your last transcript's latest changes aren't saved in its project." Neither dialog changes otherwise.
  Covered by the `unsavedInProject` specs in `transcriptLink.spec.ts`, by new cases in `GlossaryView.spec.ts` and
  `SettingsView.spec.ts`, and by "before Reconnect, Clear saved data and Run warn that the change isn't in the
  project" in `project-add.e2e.ts`. Not changed: **Try again** and **Start again** on Output replay a run that was
  already confirmed and don't ask again.

#### BUG-5 — Re-sent agent requests duplicate streamed text (Low)

- **Where:** [src/providers/llm/claudeAgent.ts:245–285](../src/providers/llm/claudeAgent.ts#L245) (JSON retry),
  [src/providers/llm/geminiAgent.ts:246–317](../src/providers/llm/geminiAgent.ts#L246) (malformed-call retry),
  [src/stores/chat.ts:428–445](../src/stores/chat.ts#L428).
- **What:** both providers emit `text` events as deltas arrive, then re-send the same request when a tool call
  can't be parsed. The chat store appends every delta to `draft`. While the retry streams, the answer shows the
  first attempt's text followed by the second's. A finished answer is fine (it is replaced by `result.text`), but
  **Stop** during the retry saves the duplicated draft to the chat file. With Claude, the failed attempt's tokens are
  also never added to `usage` (`finalMessage()` throws before they are counted), so the cost line under-reports it;
  Gemini counts them before it retries.
- **Suggestion:** have the provider emit a `retry` event (or buffer text per attempt) so the store can roll the
  draft back to the last settled point; count the failed Claude attempt's usage where the SDK exposes it.

#### BUG-6 — Transcription retries reuse the captured key and options (Low)

- **Where:** [src/stores/job.ts:178–181](../src/stores/job.ts#L178),
  [src/ui/components/JobStatus.vue:85–95](../src/ui/components/JobStatus.vue#L85).
- **What:** `retry()` replays `lastSnapshot`, including `apiKey`, language, speakers and keyterms. **Try again** is
  hidden for `auth` and `validation`, but shown for `quota`, `rate_limit`, `server` and `network`; **Start again**
  after Cancel always replays.
- **Scenario:** "Your ElevenLabs account has no remaining credits" → the user pastes a key with credit in Settings →
  **Try again** sends the old key and fails the same way. The translation store deliberately reads the key at run
  time for this reason ([translation.ts:65](../src/stores/translation.ts#L65)); the job store is inconsistent.
- **Suggestion:** keep the file from the snapshot but re-read the key (and arguably the options) on retry.

#### BUG-7 — "The better of the two" summaries prefers fewer quotes, not better ones (Low)

- **Where:** [src/features/summary/summarise.ts:60](../src/features/summary/summarise.ts#L60).
- **What:** a reply over the 1/3 failure rate is retried, and the one with fewer `droppedQuotes` is kept. A first
  reply with 9 quotes and 4 dropped (5 verified) loses to a second with 2 quotes and 1 dropped (1 verified), and a
  reply with no quotes at all always wins.
- **Suggestion:** compare the failure rate, with verified quotes as a tie-breaker.

#### BUG-8 — One stubborn turn can make a translation impossible (Low)

- **Where:** [src/features/translation/translate.ts:106](../src/features/translation/translate.ts#L106) and the
  retry loop at `:65–89`.
- **What:** a batch whose reply has an empty text for any id is `bad_output`, retried once, then the run stops.
  **Resume** sends the same batch again. If a model consistently returns an empty string for a turn (a turn that is
  only a non-lexical sound or a name it decides not to translate), the session can never be translated. For a
  non-English session, **Add to project** still saves the transcript (that step comes first), but its translate and
  summarise steps, and any later **Summarise**, can't complete.
- **Suggestion:** after the retry, accept the original text for turns that still come back empty (and record it),
  rather than failing the whole run.
- **Status:** Fixed on 3 November 2026 with the suggestion, recorded as D42. The first reply is checked as before.
  On the retry, `checkReply` takes `keepOriginal`: if the only problems left are empty texts, those turns keep their
  original text as their English. This applies to at most a third of the batch's turns, and always to one, so a
  batch of one turn can't get stuck. A reply that leaves more turns empty still fails, as one with a missing, extra or
  duplicate id does. The kept text counts as current English (D39) until the turn is edited, so **Update English…**
  doesn't offer it again, and the pipeline goes on to the summary. Recorded as a rule only (maintainer): no saved
  marker and no "Not translated" tag, because the English view shows the original text. `docs/USER_GUIDE.md` §6,
  `reference/llm-providers.md`, Phase 6's handoff and the CHANGELOG are updated. Covered by:
  - five `translateTranscript` cases and two `checkReply` cases in `translate.spec.ts`;
  - a case each in the `translation.spec.ts` and `pipeline.spec.ts` stores, the second being Add to project with a
    German session;
  - "a turn that comes back empty twice keeps its original text, and the translation finishes" in
    `translate.e2e.ts`.

  With `keepOriginal` off in `translateBatch`, the four cases that keep an original and the e2e case fail.

#### BUG-9 — Re-selecting the open chat doesn't show its latest version (Low)

- **Where:** [src/stores/chat.ts:657](../src/stores/chat.ts#L657).
- **What:** `open()` returns early when the chat is already open. If a colleague (or the same user on another
  computer) has added to it, selecting it in the Chats tab does nothing; the user has to open another chat and come
  back. D29 leaves live updating out of scope ("opening it again shows the latest"), so this doesn't break the
  decision, but selecting the open chat again is the obvious way to open it again, and it shows nothing new.
- **Suggestion:** compare the file's stat or `updatedAt` with `target` and reopen when it changed and nothing is
  running.

#### BUG-10 — Gemini maps every `TypeError` to a network failure (Low)

- **Where:** [src/providers/llm/gemini.ts:328](../src/providers/llm/gemini.ts#L328) (also used by the agent).
- **What:** `fetch` rejects with `TypeError` on a network failure, but so does any programming error in the SDK or
  the adapter (reading a property of `undefined` in an unexpected chunk). Those show "Couldn't reach Gemini. Check
  your internet connection…" and are marked retryable.
- **Suggestion:** check `navigator.onLine`, or match on the SDK's fetch failure, before choosing `network`.

#### BUG-11 — Empty language code leaks into the export (Low)

- **Where:** [src/providers/transcription/elevenlabs/mapper.ts:32](../src/providers/transcription/elevenlabs/mapper.ts#L32)
  sets `languageCode: ''` when the response has none; [src/features/export/fileName.ts:19](../src/features/export/fileName.ts#L19)
  then names the file `… - transcript ().docx`, and the Word header reads "Language: (detected)".
- **Suggestion:** fall back to the request's language hint, or leave the part out when the name is empty.

### 4.2 Design flaws and data-integrity risks

#### DES-1 — Older builds delete fields that newer builds wrote (Medium)

- **Where:** every persisted schema uses plain `z.object`, which strips unknown keys (verified: `{ a, futureField }`
  parses to `{ a }`): [storage/schemas.ts:35](../src/storage/schemas.ts#L35) (`TranscriptDocSchema`),
  [storage/projectFiles.ts:32–61](../src/storage/projectFiles.ts#L32), [storage/chatFiles.ts:43](../src/storage/chatFiles.ts#L43).
  Writers serialise the parsed object back: `saveBrief` spreads the parsed project
  ([stores/project.ts:798](../src/stores/project.ts#L798)), an opened transcript is saved from the parsed doc, a
  continued chat from the parsed messages.
- **Why it matters:** D18 says "an older release may still open data a newer one wrote", and that a new optional
  preference "isn't a shape change". D26 carried that over to files when it added `provider` to summary files:
  "Adding an optional field doesn't change the shape (D18), and older builds ignore it." In a shared OneDrive
  folder, colleagues will run different versions (the HTML file is downloaded by hand; the Store app updates
  itself). The first older client that edits the brief, a transcript, or continues a chat silently removes the
  newer fields for everyone. Nothing is lost today, but the next "optional field" will be.
- **Suggestion:** make persisted object schemas `.loose()` (keep unknown keys) and write back the original object
  with the changes applied; or have readers refuse to *write* a file whose `schemaVersion`/fields they don't fully
  understand. Record the policy in D18.
- **Status:** Fixed on 3 November 2026 with the first suggestion, recorded as D38 (D18 points to it). The schemas of
  data DeScribe writes back are `z.looseObject` at every level:
  - the project file and its brief;
  - `TranscriptDocSchema`, which reads both the project's transcript files and the last transcript in IndexedDB;
  - chat files, their author, their messages and the messages' activity.

  Two writers rebuilt objects field by field and now start from what was read. `saveBrief` spreads the brief as well
  as the file. The chat store keeps the file it opened: saving your own chat again spreads the file and its author,
  and every message that was read is written back exactly as it was. Output's transcript edits already spread, so
  they needed no change. Left as they are, since they are replaced rather than written back:
  - summary files;
  - the transcript file's wrapper (new fields go in `doc`);
  - the top level of a copy of a colleague's chat (its messages keep their fields);
  - the corpus cache and the transcript link.

  1.0.0 and 1.1.0 still strip unknown fields, so while colleagues may run them, a field whose loss would matter needs
  a `schemaVersion` bump (D38). Covered by "keeps fields a newer build added …" cases in `schemas.spec.ts` (new),
  `projectFiles.spec.ts`, `chatFiles.spec.ts`, `idb.spec.ts`, `project.spec.ts`, `transcriptLink.spec.ts` and
  `chat.spec.ts`; each fails with the fix reverted.

#### DES-2 — Translations go stale silently, and release 2 depends on them (Medium)

- **Where:** [stores/pipeline.ts:61–65](../src/stores/pipeline.ts#L61) (`needsTranslation`),
  [features/summary/check.ts](../src/features/summary/check.ts) and
  [features/agent/answer.ts:145](../src/features/agent/answer.ts#L145) (quotes are checked against `englishText`).
- **What:** D19 accepted that editing an original doesn't update or flag its English, when the English was only a
  view and an export. In release 2 the English is the research object: summaries are written from it, the agent
  reads and quotes it, and quotes are verified against it. `needsTranslation` only checks that every turn id has a
  translation, so after a German transcript is corrected, **Regenerate** summarises the uncorrected English, and the
  stale-summary badge disappears. Nothing tells the researcher.
- **Suggestion:** store a hash of each turn's source text with its translation (or the doc's `transcriptHash` at
  translation time), show "English out of date" when it differs, and let the pipeline re-translate only the
  changed turns. This is a decision for DECISIONS.md, since it revisits D19.
- **Status:** Fixed on 3 November 2026 with the first suggestion, recorded as D39 (D19's bullet points to it). A
  translation now keeps `sourceHashes`, the hash of each turn's text when it was translated
  (`domain/translation.ts`). A turn whose text changed since has out-of-date English:
  - `toSessionText` gives it `en: null`, so search's English, summaries, the agent and the quote checks don't use
    it, and `transcriptHash` leaves it out. A summary made from it is therefore out of date. A transcript with no
    changed turns keeps its hash, so existing summaries stay current.
  - `needsTranslation` and the new `lacksEnglish` see it, so **Summarise**, **Regenerate** and **Add to project**
    translate first. `translateTranscript` keeps the English whose turn is unchanged and sends only the batches
    with a changed turn. This also replaced BUG-3's `unchangedTexts`: a partial translation carries its hashes, so
    **Resume** re-translates a turn edited after a failure too.
  - On Output, the English view tags each changed turn "Changed since translation", **Translate** becomes **Update
    English…** (only the changed turns), and the export dialog's English option says how many turns are out of date.
    The export still writes the stored English.
  - The agent's `read_transcript` marks such a turn `(original)`, as search results do, and says it can't be quoted.
    This tool text was checked against the `claude-api` skill.

  A translation from before the fix has no hashes and counts as current, as it did before. The first edit with this
  build records the turns as they were, so later edits are noticed. 1.0.0 and 1.1.0 drop the field when they save,
  which falls back to the same behaviour; D39 explains why that needs no `schemaVersion` bump. The corpus cache isn't
  cleared (D39 covers the one gap). `docs/USER_GUIDE.md` and Phase 9's handoff are updated.
  Covered by `domain/translation.spec.ts` (new) and new cases in:
  - `sessionText.spec.ts`, `schemas.spec.ts` and `translate.spec.ts`;
  - the `pipeline.spec.ts`, `translation.spec.ts` and `transcript.spec.ts` stores;
  - the `TurnList`, `TranslateButton`, `TranslateDialog`, `ExportDialog`, `ExportButton`, `SessionSummary` and agent
    `tools` specs;
  - "editing a turn marks its English out of date; Update English translates only its batch" in `translate.e2e.ts`.
    `edit.e2e.ts` now expects **Update English…** after an edit. Both specs wait for the autosave with
    `savedTurnText`, which moved from `edit.e2e.ts` to `helpers.ts`.

  With `translationTexts` reverted on its own, three of the new cases fail (two in `sessionText.spec.ts`, one in
  `pipeline.spec.ts`).

#### DES-3 — Diagnostic detail is collected and then thrown away (Medium)

- **Where:** `ProviderError.opts.detail` is filled carefully in every provider (ElevenLabs request ids and error
  codes, Claude refusal categories and API reasons, Gemini status and quota ids, translation batch problems), and
  redacted for secrets. `grep` finds no reader outside `errors.ts`: it is never shown, logged or exported.
- **Why it matters:** when a colleague reports "Claude couldn't process the request" or "Claude declined to process
  this text", there is no request id, refusal category or reason to act on. Several live checks are still open, so
  field reports are the main source of evidence.
- **Suggestion:** a `<details>` "Technical details" under error messages (D13 allows detail behind `<details>`), or
  a Copy-details button. `console.warn` for genuine provider faults is also allowed by AGENTS.md.
- **Status:** Fixed on 3 November 2026 with the first suggestion, recorded as D41. `technicalDetails` in
  `providers/errors.ts` turns an error into "<kind> · HTTP <status>" and its detail, and the new `ErrorDetails.vue`
  shows that, with the build (`DeScribe v…`), in a closed **Technical details** under the message. The text selects in
  one click, so there is no Copy button. It appears under transcription (`JobStatus`), translation
  (`TranslateButton`), pipeline (`PipelineStatus`, `SessionSummary`, the queue's stop in `SessionList`) and chat
  (`ChatMessage`, `ChatCompaction`) errors, only when the error has a status or a detail. It is outside each error's
  alert, so screen readers still hear only the message. Every saved key is redacted from it as well: providers
  already redact the key they used, but stores wrap unexpected errors with their raw message, which was never shown
  before. Not changed:
  - key tests in Settings, whose providers return only a message;
  - folder errors, which have no detail;
  - Claude's request id, which `toProviderError` in `claude.ts` doesn't record (changing it needs the `claude-api`
    skill);
  - `console.warn`.

  `docs/USER_GUIDE.md`'s troubleshooting table and the CHANGELOG say where to find it. Covered by `technicalDetails`
  cases in `errors.spec.ts`, by `ErrorDetails.spec.ts` and `ChatMessage.spec.ts` (both new), by a case in each of
  the `JobStatus`, `TranslateButton`, `PipelineStatus`, `SessionSummary`, `SessionList` and `ChatCompaction` specs,

#### DES-4 — A copied project folder is the same project to DeScribe (Low)

- **Where:** the project id from `describe-project.json` keys the corpus cache
  ([storage/corpusCache.ts:40](../src/storage/corpusCache.ts#L40)), the Output tab's link (D25,
  [stores/transcript.ts:126](../src/stores/transcript.ts#L126)) and the pipeline and chat resets.
- **Scenario:** a researcher duplicates a project folder to start a new study from it. Explorer keeps file sizes
  and modification times, so the stats match too. With the copy open, the Output tab's link to a transcript in the
  original saves into the copy without a conflict, and `pruneCorpusCache` for one copy deletes the other's cache
  entries.
- **Suggestion:** keep the directory handle with the link and check `isSameEntry`, or warn when a project id is
  seen at a second handle.

#### DES-5 — No sync between tabs (Low)

- **Where:** [stores/settings.ts](../src/stores/settings.ts), [stores/glossary.ts](../src/stores/glossary.ts).
- **What:** keys, prefs and the glossary are read once into refs and written on change; there is no `storage`
  event listener. Two open tabs diverge, and each change overwrites the other's. After **Forget all keys** in one
  tab, the other still holds every key in memory and keeps using them; editing a key there writes that key back, and
  turning **Remember keys** on or off there writes all of them back. For a single HTML file opened by double-click, a
  second tab is easy to end up with.
- **Suggestion:** listen for `storage` events and reload the affected refs.

#### DES-6 — A failed key write still removes the other copy (Low)

- **Where:** [storage/secrets.ts:28–29](../src/storage/secrets.ts#L28).
- **What:** `saveKey` writes to the chosen area and then removes the key from the other one, whether or not the
  write succeeded (`writeJson` returns `false` on quota or blocked storage). Moving keys with "Remember keys" then
  loses them after a reload.
- **Suggestion:** remove from the other area only when the write returned `true`.

#### DES-7 — Test hooks and global UI state in production modules (Low)

- **Where:** `setTranscriptionProviderForTests`, `setLlmProviderFactoryForTests`, `setAgentProviderFactoryForTests`
  in [providers/index.ts](../src/providers/index.ts) sit in a production module. Only specs call them, so the build
  drops the setters themselves, but the `override ??` checks in the getters ship.
  [ui/composables/useProjectUi.ts:9](../src/ui/composables/useProjectUi.ts#L9) is a module-level `reactive` outside
  Pinia (with a `resetProjectUi` for tests), so the selected session, the sidebar tab and the chat pane's mode aren't
  reset by **Clear saved data** or a project switch, and the state isn't visible in devtools with the rest.
- **Suggestion:** inject providers through a small Pinia store or `provide`, and move the project UI state into a
  store.

### 4.4 Performance and scalability

#### PERF-1 — Rescans stat every file, one at a time, on every focus (Low)

- **Where:** [storage/projectFiles.ts:159–166](../src/storage/projectFiles.ts#L159),
  [storage/chatFiles.ts:86–92](../src/storage/chatFiles.ts#L86), triggered by `focus` and `visibilitychange`
  ([stores/project.ts:649–654](../src/stores/project.ts#L649)).
- **What:** each listing awaits `getFileHandle` + `getFile` per entry in sequence. At the 300-hour scale (≈600
  session files plus chats) that is ≈600+ sequential round trips through OneDrive's filter driver every time the
  window regains focus. The file *reads* are deliberately sequential (reference doc Rule 6); the stats may not need
  to be.
- **Suggestion:** measure it in `project.perf.ts` with a realistic file count; if it's slow, stat in small parallel
  batches or only re-stat when the directory listing changed.

#### PERF-2 — The corpus cache only shrinks for the open project (Low)

- **Where:** [storage/corpusCache.ts:83–96](../src/storage/corpusCache.ts#L83).
- **What:** `pruneCorpusCache` removes stale entries of the current project only. A researcher who opens several
  projects over time keeps every project's text (~30 MB per 300-hour project, T12) in IndexedDB until **Clear saved
  data**.

## 5. Checked and found sound

These were looked at specifically and need no change:

- **Claude integration** against the `claude-api` skill: current model ids; `effort: medium` set explicitly (Opus 5.5
  defaults to `medium`, Sonnet 5.5 to `high`); adaptive thinking with no `disabled` or `budget_tokens`; no forced
  `tool_choice` (a 400 on these models); `fallbacks: 'default'` with `server-side-fallback-2026-07-01`; `stop_reason`
  checked for `refusal` and `max_tokens` before content is read; thinking and `tool_use` blocks before a mid-output
  fallback boundary dropped when echoing; the conversation append-only, so preserved thinking holds; three cache
  breakpoints within the limit of four; `eager_input_streaming` with zod validation of every tool input.
- **Security:** no `v-html` anywhere; model output is parsed into text blocks, never HTML; the CSP is verified at
  build time and forbids `unsafe-eval` (zod runs jitless); keys are trimmed, never logged, and redacted from error
  text; the desktop shell grants no IPC capability and only opens `http(s)` links externally; the agent's tools are
  read-only.
- **Quote integrity (T13):** the quote check is greedy in order, which is correct for ordered runs; summaries and
  answers show the transcript's own words; unverified quotes can't be copied.
- **Concurrency guards** that work: stale-run checks (`isCurrent`, `seq`, `writes`) in the job, translation, pipeline,
  project and chat stores; the serialised folder-save queue in the transcript store; chat saves that fork on
  `changed` instead of overwriting.
- **Storage:** every `localStorage`, `sessionStorage` and IndexedDB access is wrapped and degrades quietly; prefs
  fall back field by field.
- **Accessibility:** real buttons and labels, `aria-live` regions for status changes, focus management on view
  changes and dialogs, and an axe pass in e2e.
